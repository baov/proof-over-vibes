# AGENTS.md

## Harness

This project has a deterministic enforcement layer generated by the `codebase-harness` skill. Agents must comply with these rules.

### Executable invariants

The architecture rules are made executable by scripts in `tools/harness/`. Full list and statuses in [docs/technical/invariants.md](docs/technical/invariants.md).

- Before any commit, run: `bash tools/harness/run_all.sh`
- Each check's messages include the remediation to apply: read them before looking elsewhere
- To understand an invariant without checking it: `python3 tools/harness/check_layers.py --explain`
- Unit tests: `mvn test`. The architecture test is run by the harness (`-Pinvariants`), not by the default build.

### Test-case bridge to real tests

Every scenario under `docs/business/test-cases/` carries a YAML front-matter pointing to its automated test (`automated_test: src/test/java/<path>/<Class>Test.java::<method>`). `tools/harness/check_test_coverage.py` checks the consistency.

- Adding a test-case: fill in the front-matter (`automated_test` field, or `status: pending`)
- Adding a test: check it has a matching test-case, otherwise create one

### Mutation testing

Tests written without line-by-line human review are kept in check by mutation testing. A green test is not proof: only a killed mutant is.

- Scope and threshold: see INV-003 in [docs/technical/invariants.md](docs/technical/invariants.md) (`domain` and `application`; no threshold yet)
- Run locally: `bash tools/harness/run_mutation.sh --scope diff`
- A surviving mutant is dealt with by adding a test that expresses the unprotected **behavior**, never a test written to kill the mutant. If the mutant matches no behavior that counts, exclude it explicitly in `pom.xml` with a comment justifying it
- Never lower a threshold to get CI passing: that is the signal that a behavior has lost its protection
